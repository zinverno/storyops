# Continuity policy

Goal: no publication starts from zero.

```
previous publication → what happened afterwards → what changed → new conflict/discovery → this publication
```

instead of

```
project origin → project origin again → project origin again
```

## Reading `.editorial/continuity.md`

- **Already covered** per project: origin, architecture revisions, updates.
- **Concepts explained** vs **only mentioned**. Coverage is cross-platform, but
  depth matters: a concept mentioned in a short Telegram post is *mentioned*,
  not *explained*. A full Habr explanation may still be valuable.
- **Explained more than once**: stop re-explaining; link.
- **Promises to readers** and **open questions**: `open` threads are strong
  story candidates; `possibly-addressed` is a lexical guess, verify it.

## Rules for drafting

1. Link the continued publication in the first section.
2. Summarise previously explained concepts in at most one or two sentences + link.
3. If the new story contradicts an earlier publication (architecture changed),
   say so explicitly: that is often the most interesting part.
4. Close open threads you are resolving ("в прошлый раз я обещал…").
5. After publishing, import or sync the new publication so memory stays current.

Continuity data is heuristic. Treat it as leads to verify.
