Как устроен Notegarden: разовый аудит заметок изнутри

В прошлой статье я рассказал, зачем мне понадобился Notegarden. Теперь про то, как он устроен. Архитектура у первой версии намеренно простая: аудит запускается один раз, проходит по всему хранилищу и выдаёт отчёт. Никакого состояния между запусками нет.

Архитектура аудита

Аудит состоит из трёх частей. Раннер в src/audit/runner.ts обходит хранилище и строит индекс заметок. Правила в src/audit/rules.ts получают индекс и возвращают находки. Модуль отчёта в src/report/markdown.ts превращает находки в markdown.

export async function runAudit(vault: string): Promise<Finding[]> {
  const index = await buildIndex(vault);
  return rules.flatMap((rule) => rule.check(index));
}

Индекс хранит для каждой заметки путь, заголовки, исходящие ссылки и теги. Входящие ссылки считаются вторым проходом, когда все заметки уже прочитаны. Индекс строится заново при каждом запуске аудита, и это главное упрощение первой версии.

Правила

Каждое правило — это объект с идентификатором, описанием и функцией check. Правило ничего не знает про файловую систему: оно получает готовый индекс и возвращает список находок. Благодаря этому правила легко тестировать на маленьких синтетических индексах, без реального хранилища.

export const orphanNotes: Rule = {
  id: 'orphan-note',
  check: (index) => index.notes.filter((n) => n.incoming.length === 0).map(toFinding),
};

Находка в первой версии — это просто запись: правило, заметка, сообщение. У находки нет истории и нет статуса. Если запустить аудит завтра, он найдёт те же самые проблемы и не будет знать, что вчера они уже были.

Отчёт

Отчёт группирует находки по правилам и сортирует по количеству. Сверху идёт сводка, дальше списки со ссылками на заметки. Так как ссылки в формате вики, по ним можно кликать прямо в Obsidian и сразу исправлять.

Отчёт перезаписывается при каждом запуске. Сравнить два отчёта можно только через diff в git, и это неудобно: порядок строк меняется, если в хранилище добавилась хотя бы одна заметка.

Почему аудит разовый

Разовый аудит было проще всего написать и проверить. Я хотел сначала понять, какие правила вообще полезны, и не тратить время на хранение состояния. Для хранилища на четыре тысячи заметок полный проход укладывается в секунды, поэтому инкрементальность казалась преждевременной оптимизацией.

Но у этого решения есть цена. Аудит не помнит, какие находки я уже видел и сознательно оставил. Он не показывает динамику: стало ли хранилище лучше за месяц или хуже. И каждое новое правило приходится встраивать в общий проход, который постепенно разрастается.

Что дальше

Планирую сделать анализ постоянным, чтобы не прогонять весь аудит с нуля при каждом запуске и видеть, как меняется состояние хранилища. Открытый вопрос — как хранить историю находок между запусками: в файлах рядом с заметками или в отдельной базе.
