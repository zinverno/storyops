# Notegarden помнит находки: как разовый аудит стал моделью здоровья

Каждый регулярный запуск Notegarden заканчивался одинаково: отчёт на несколько экранов, где свежая битая ссылка стояла рядом с заметкой-сиротой, которую я видел уже много раз и сознательно оставил в покое. Аудит не отличал одно от другого, потому что отчёт каждый раз строился с нуля и ничего не помнил о прошлых запусках.

Можно сказать, что у аудита была профессиональная амнезия: каждый запуск он знакомился с хранилищем заново.

## Почему перезаписываемый отчёт казался нормальным

Как устроена первая версия, я уже разбирал в [прошлой статье](https://habr.com/ru/articles/900002/): раннер строит индекс хранилища, правила проверяют индекс и возвращают находки, отчёт в markdown перезаписывается. Для разовой проверки этого хватало.

Сначала перезаписываемый отчёт и мне казался нормальным решением. Потом оказалось, что он отвечает за два разных смысла: что сломано сейчас и что я уже видел и решил не трогать. Первое отчёт показывал хорошо, второе не умел выразить совсем. Заодно он не мог ответить на простой вопрос, становится ли хранилище лучше или хуже со временем.

## Находка получает жизненный цикл

Решение записано в ADR-0003: заменить разовый аудит постоянной моделью здоровья. Главное изменение случилось с самой находкой. Finding перестал быть просто строкой в отчёте. Теперь у него есть состояние, и допустимые переходы описаны явно:

```ts
const allowed: Record<FindingState, FindingState[]> = {
  open: ['acknowledged', 'resolved'],
  acknowledged: ['open', 'resolved'],
  resolved: ['open'],
};
```

Находка бывает открытой, подтверждённой или исправленной. Из resolved можно только вернуться в open: если исправленная проблема появилась снова, её нельзя молча пометить как уже просмотренную. Подтверждённые находки больше не всплывают в каждом отчёте, пока заметка не изменилась.

## Где хранить память

Как только у находки появилось состояние, его нужно хранить между запусками. JSON-файлы отчётов для этого не подходили, мне нужна была история находок. Хранение переехало в SQLite, схему создаёт миграция:

```sql
CREATE TABLE findings (id TEXT PRIMARY KEY, rule TEXT NOT NULL, note TEXT NOT NULL, state TEXT NOT NULL, first_seen TEXT NOT NULL);
```

Два ограничения я при этом сохранил. Хранилище остаётся локальным, без сервера. Сами заметки Notegarden по-прежнему не трогает.

## Оценка здоровья по папкам

Поверх сохранённых находок появилась модель здоровья: для каждой папки считается оценка из числа открытых находок и числа заметок. Пересчитываются только папки, в которых что-то изменилось. Полный пересчёт при каждом запуске повторил бы главный недостаток разового аудита, только в новой обёртке.

Сколько времени это экономит, я пока не знаю: замеров производительности инкрементального пересчёта нет.

## Что стало с аудитом

Сам аудит превратился в инкрементальный конвейер анализа (`src/analysis/pipeline.ts`), а разовый раннер я удалил из репозитория. Всё это вышло в версии 0.2.0 вместе с анализом знаний, которому стоит посвятить отдельную статью.

У памяти есть цена. Хранилище рассчитано на один процесс: два анализа одного хранилища одновременно не поддерживаются, это прямо записано в последствиях ADR-0003.

## Что дальше

Открытым остаётся вопрос, как показывать динамику оценки здоровья, чтобы она не превращалась в шум. График динамики в отчёте я планирую, но его пока нет.
